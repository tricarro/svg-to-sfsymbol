# Implementation plan: Retain fill on mixed stroke+fill preprocessing

**Status:** Approved  
**PRD:** `1_ProductRequirementsDocument.md` (this folder)  
**Date:** 2026-04-06

---

## Overview

Mixed-route preprocessing today turns each stroke+fill graphical element into a fill-stripped stroke copy plus a second path that traces the fill boundary as a stroke. This plan replaces that branch with a single pass-through: serialize the original element so fill and stroke paint stay on one shape. Fill-only elements inside a mixed SVG still use `fillBoundaryToStrokedPathMarkup` unchanged. Unit tests and compiled `server/dist` output are updated to match; HTTP routing and `mixedIconToStrokedSvg` signature stay the same.

---

## Architecture decisions

### Stroke+fill handling

Emit `serializeElement(el)` for `hasS && hasF` instead of clone/strip/boundary-append. Matches the PRD: no duplicate boundary path for those elements; `text` with stroke+fill is treated like other graphical tags (fill retained, no special case).

### Dead code removal

`stripFillFromElement` and `deepCloneElement` are only used by the stroke+fill branch; remove them and drop the `deepCloneElement` / `localTag` imports if nothing else in the file needs them. Keep `fillBoundaryToStrokedPathMarkup` and its phase4 imports for the fill-only-within-mixed path.

## Risk flags & open technical questions

- **Downstream square pipeline:** Filled geometry on stroke+fill elements may behave differently than the old double-stroke heuristic; watch for template or export oddities on real assets (PRD-accepted risk).
- **Output shape:** Count of `<path>` elements per stroke+fill shape drops by one (no boundary duplicate); anything that diffed raw markup could see a change.

## Out of scope
